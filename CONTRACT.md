# Contract

Dibs asks whether many agents can share one backlog safely when every claim is a lease that expires unless it is renewed, so a claim held by an agent that is gone returns to the backlog on its own. This file is the stub contract for the setup slice. It states the setup obligations only, and each obligation is stated so it can fail.

Obligation S1 covers seed integrity. The seed files README.md and LICENSE and .gitignore are present from the first commit, and every later change lands through a pull request rather than a direct push to main. This is covered by inspection of the repository history and by the status section of the README.

Obligation S2 covers the local gate. The test suite runs with cargo test plus the codepoint scan run through cargo, and running it needs no paid service, and the continuous integration workflow runs the same commands as the local gate. This wording is amended by the Rust port that opens Round 2. The setup wording named python and pytest alone and no network access, and the amendment replaces it under the program language ruling of 2026-11-02, which made every repo in the program a Rust crate. The amended gate keeps the no paid service term. It drops the no network access term for one stated reason, a first build fetches the crate dependencies from the public crates.io registry, and the tests themselves then run with no network access. This is covered by the tests in the tests folder and by the workflow in the .github folder.

Obligation S3 covers honest status. The README status section records the seed state and the contract state truthfully and it reports closed perfection rounds as 0 of 100 until a full cycle of work and audit and review and red team and approval has closed. This is covered by inspection of the README against this contract and against the repository history.

Obligation S4 covers synthetic content only. Every fixture and every example in this repository is synthetic and written for this repo, and no file carries a real trace or a real transcript or a real name or any private operational detail. This is covered by inspection of the repository contents before any push.

Obligation S5 covers the canonical agents file. The part of AGENTS.md above the marked line is identical to the canonical template for the program, and only the repo annex below the marked line differs for dibs. This is covered by tests in the tests folder that pin the SHA-256 digest of the part above the marked line and check the marked line and the annex.

The full contract for dibs is the first build act of this repo and it lands with the first slice. This stub is not the full contract, and no feature claim for dibs rests on this stub.

## Round 1 amendment, the claim lease protocol, slice 1

The full contract the stub promised is this amendment. It names the stub status text above as the earlier record and supersedes it, and the stub text stands so the record shows both. Obligations S1 to S5 stand unchanged above. The obligations for the protocol are DB-1 to DB-13, and each one is stated so it can fail.

### Probe preamble

The obligations below rest on behaviour probed on this machine under Python 3.12.3, not on habit.

Probe one, flock. Eight processes each ran fifty read and modify and write cycles on one shared counter file, holding an exclusive flock on a lock file across each cycle. The counter finished at exactly 400 with zero lost updates. A nonblocking exclusive acquire against a lock another process held raised BlockingIOError. After the holding process was killed, the lock was acquirable with no measurable wait, so a dead holder cannot wedge the protocol.

Probe two, rename. One writer published 300 versions of a JSON document by writing a temporary file in the same directory and renaming it over the target with os.replace. Three reader processes read the document 102978 times in total during the run and saw zero torn or partial documents, and every read parsed as one complete published version. The registry therefore publishes by rename from a temporary file in its own directory, which also keeps the rename on one device.

Probe three, token and hash primitives. The SHA-256 of the three bytes abc computed by hashlib equals the worked example digest printed in FIPS 180-4. The secrets.token_urlsafe function with 32 bytes produced 10000 unique values in 10000 samples, each 43 characters long and drawn from the URL safe alphabet. Hashing 1000 tokens took 0.006 seconds, so checking a presented token against a stored hash costs nothing the protocol will notice.

### The obligations

Obligation DB-1 covers atomic claims. Every mutating operation runs its whole read and evaluate and modify and write cycle under one exclusive flock on the lock file beside the registry, and the new state is published by renaming a complete temporary file over the registry. Many processes claiming one item at the same instant produce exactly one winner, and every loser receives a refusal that names the standing holder. This is covered by concurrency tests that race processes on one item and on distinct items.

Obligation DB-2 covers lazy and total expiry. There is no daemon and no timer. Every operation and every read that evaluates lease state does so against the instant it is given, a lease is live at instants strictly before its expiry instant, and a lease is expired at its expiry instant itself. History is the one read that evaluates no lease state, because it returns the recorded events, and it takes no instant. An expired lease never blocks a claim, never shows as live on the board, and never accepts a renew. A claim or a renew carries a time to live that is a positive integer number of seconds, at most 31536000 seconds, and any other time to live is refused before any state changes. A time to live inside that bound whose addition to the current instant or to a standing expiry would run past the last representable instant is likewise refused as an invalid time to live before any state changes. This is covered by tests that pin the exact expiry instant with injected times and never sleep.

Obligation DB-3 covers time as an input. Every library operation that evaluates lease state takes the current instant as an explicit argument. History takes no instant, because it returns the recorded events and evaluates no expiry. The command line passes the wall clock in UTC and offers no flag that overrides it, so the library tests pin expiry deterministically and the command line stays honest about whose clock it used. This is covered by the library tests with injected instants and by a command line test that the surface carries no time override flag.

Obligation DB-4 covers possession by token. A successful claim returns a fresh unguessable token once, drawn from the secrets module, and the registry stores only the SHA-256 hash of that token. Renew and release and complete must present the token, and a wrong token fails even when the holder name is right. Neither the token nor its hash appears in board output, in history output, or in any history event. This is covered by tests that present a wrong token under the right name, that search the registry bytes for a live token, and that search board and history output for tokens and hashes.

Obligation DB-5 covers fencing by epoch. Every successful claim increments the epoch of the item, the first claim carries epoch 1, and the epoch stands on the board where other systems can fence with it. Renew and release and complete must present the standing epoch, and an operation carrying a stale epoch fails. After a takeover the previous holder holds a stale token and a stale epoch and every operation it attempts fails. This is covered by takeover tests that drive the old holder against the new lease at renew and release and complete.

Obligation DB-6 covers strict reading. The registry is one JSON document under the format name dibs-registry/1, and reading it refuses duplicate keys at any level, a wrong format name, a wrong type in any field, and any unknown field, each as a typed corruption error and never a traceback and never a silent repair. A registry that cannot be read blocks every operation, reads included, and no operation resets it or writes over it. This is covered by a damage battery that corrupts the document in each named way and checks the error type and that the registry bytes stand unchanged afterwards.

Obligation DB-7 covers history inside the same document. The history lives in the registry document itself, so a state change and its history event publish in the same rename and the record cannot disagree with the state. Every successful mutation appends exactly one event, events carry sequence numbers that start at 1 and grow by 1 with no gaps, and the event kinds are offered and claimed and renewed and released and completed and taken over. A claim that lands on an expired lease is recorded as taken over and the event names the previous holder. A completed item keeps its full history and the history stays readable after completion. This is covered by tests that walk a full item life and read the history back at each step, and by the concurrency tests that check the sequence for gaps after racing claims.

Obligation DB-8 covers name and note validation. An item id and a holder id are one component of lowercase letters and digits and hyphens and underscores, starting and ending with a letter or a digit, at most 64 characters long, and any other shape is refused at every operation that takes the name. An offer note is a string of at most 200 characters. This is covered by edge tests on both sides of each part of the rule for item ids and holder ids and by a note length test at the bound.

Obligation DB-9 covers completion as terminal. A completed item accepts no claim and no renew and no release and no further complete, and its id cannot be offered again in this slice, so one id can never carry two histories. History is the one operation a completed item still accepts. This is covered by tests that drive every other operation against a completed item and against its id.

Obligation DB-10 covers board honesty. The board lists open items in offer order, each with its state evaluated at the read instant, its holder and its lease expiry and its epoch when it stands claimed, and no holder and no expiry when it stands open. An item whose lease has expired at the read instant shows as open. A completed item never stands on the board. This is covered by tests that read the board before and after an expiry instant and across a completion.

Obligation DB-11 covers refusal shapes. A claim against a live lease fails and names the standing holder. A renew extends the standing lease from its current expiry by the time to live, never from the instant of the renew. A renew against an expired lease fails, because the lease it would extend no longer stands. Renew and release and complete against an item that stands open fail. Every operation against an item the backlog does not hold fails as not found, and an offer of an id that already stands in the backlog fails. This is covered by a refusal test for each named shape.

Obligation DB-12 covers a missing registry. When the registry file does not stand, board and history read as an empty backlog and create nothing, and the first mutating operation creates the registry file and any missing parent directories and then proceeds. This is covered by tests that read and then mutate against a path where nothing stands yet.

Obligation DB-13 covers the slice 1 limits, stated so a later slice retires them by amendment rather than by drift. Expiry is evaluated on access only, with no daemon and no notifications and no watchers. The board lists items in offer order and there are no priorities and no queues. The protocol is one registry file and its lock on one machine for callers who share the filesystem, with no network service and no federation across files. A holder that loses its token has no recovery path and loses the lease at expiry. The history is unbounded in this slice and no compaction runs. This is covered by inspection of the slice against this list.

Design note, the Round 4 compaction examination. DB-13 states that the history is unbounded in this slice and no compaction runs, and the Round 4 design pass examined retiring that limit under the standing format. The examination found that the history a registry carries is the complete record of the operations that produced its standing state, that every mutation appends exactly one event and no operation removes one, that the sequence numbers are positions the reader checks against the standing order, and that the epochs standing on items and events count claims a retired record would no longer show. A compaction under dibs-registry/1 would therefore write a document no run of the operations could have written, and would shorten the answers the history operation returns, so the limit stands for this format and its retirement is a format decision for a later round and not a slice of this one. The design record stands outside this repo in the chat's Round 4 files.

### Repair note

The obligations above were amended once during Round 1, after the three reviews of the first build. This note is that amendment record, and the earlier wording of DB-2 and DB-3 stands in the review record on the pull request.

DB-2 gained the time to live ceiling of 31536000 seconds and the rule that an addition running past the last representable instant is refused as an invalid time to live, because a very large time to live escaped the first build as an unhandled overflow and printed a traceback at the command line. DB-2 and DB-3 now scope their claims about instants and expiry to the operations that evaluate lease state and name history as the exception, because history returns the recorded events and evaluates no expiry. The stored document validators gained a type check ahead of the status and kind membership lookups, because a stored list or object in those fields raised an untyped error instead of a corruption error. Two error messages were reworded so each names the case it fires on, the epoch mismatch message and the stored name message for the fields of a history event. The build also consolidated the shared lease ending and board row code and gave the instant formatter a public name, and both changes are behaviour neutral and carry no obligation change.

## Port amendment, the Rust conversion opening Round 2

Amendment, recorded with the Rust port that opens Round 2. The obligations DB-1 to DB-13 above stand unedited, and the implementation that carries them changes. The Python package of Round 1 is replaced by a Rust crate. The library carries the registry and the claim lease protocol, the token hashing, the expiry evaluation at an injected instant, and the event history. The dibs binary carries the command line with the Python surface, the same subcommands and stdout lines and error lines and exit codes, and its argument parser mirrors the Python parser down to its usage texts and its parser error messages and its acceptance of unambiguous option prefixes. The codepoint scanner is ported from the fleet template in std only Rust. Obligation S2 is amended inside its own paragraph above, in the form the conversion of deadbolt set, with the program language ruling of 2026-11-02 named as its reason.

The equivalence standard for the port is threefold. The Round 1 test suite is translated pin for pin into the Rust suite. Eight registry files written by the Python implementation stand frozen in the tests fixtures folder with a manifest that records their hashes and their board and history truths and the tokens of their standing claims, and the Rust suite reads each one and continues its claims under Rust and checks the board and the history against the record. A fixed battery of command line and library shapes is driven side by side under the Python implementation from main and under the Rust port, with exit codes and stdout and stderr compared shape by shape, and the comparison is recorded in the gate report of the port pull request. One pin beyond translation proves the registry bytes, a mutation under the Rust port writes a registry file byte identical to the file the Python implementation writes for the same operations at the same instants.

The port adds a thin PyO3 binding over the crate as the round's second slice, landed separately after the port, because agent fleets that claim work through a library are often Python, while the port pull request itself carries no binding and the Rust suite remains the gate.

Five reshapings are named here, because the obligations and the observable behaviour are the spec and the shape of the Python code is not. The strict registry reader is a hand written Visitor over serde_json that refuses a repeated key at any level as it arrives, because serde_json alone keeps the last value of a repeated key and says nothing, where the obligations require the refusal. Error messages that interpolate a value render it with the quoting the Python repr used, so the words a caller reads are the words the Python implementation printed. The registry writer is hand rolled over the fixed shape of the format and reproduces the Python byte layout including its escaping of non ASCII text and its key order, because the general JSON writer in serde_json writes non ASCII text raw where the Python writer escapes it, and the stored bytes are part of the recorded behaviour. One normalization stands with the writer. The reader accepts the keys of a document or an item or an event in any order, as the Python reader did, and the writer always writes the construction order, so a hand ordered document the Python implementation would have rewritten in its stored order is rewritten by the port in the construction order. Key order carries no meaning in the format, and no document either implementation writes differs under this rule. Instants are parsed and written by a hand written reader and writer in place of the Python datetime machinery. The stored instant family the reader accepts is the family the Python fromisoformat accepted, as probed against the Python runtime before the port was written. It takes extended and basic and week dates, any single character as the separator, a fraction written with a dot or a comma and truncated past six digits, and offsets written with a Z or with components that normalize inside a day, and it refuses a naive instant and an unparseable one with the corruption messages the Python reader raised. Names and times to live and presented epochs are validated through one value level validator that the typed operations and the command line converters and the strict reader all share. The Python implementation validated the values its callers handed it at runtime, and the Rust type system makes most wrong shapes unrepresentable at the typed surface, so the validator is where the refusal lives for the shapes that remain, and the translated pins drive it directly for those shapes. The two process race pins are restaged on operating system processes that reenter the test binary through an environment gate, the shape the language offers for the same claims, and the counts they assert are the counts the Python pins asserted.

Three differences are recorded here as safe direction divergences. The bare literals NaN and Infinity, which the Python json module reads as floating point values that then fail the field type checks one by one, are refused by this reader at parse time, inside the same corruption error and at the same exit code, and only the words of the parse detail after the shared message head differ there, as they do for every document that does not parse, because the detail text comes from the parser each implementation carries. A stored integer wider than an unsigned 64 bit integer is refused at read time by this reader where the Python reader took it, because Python integers are unbounded and the JSON reader under this one delivers an integer past that width as a floating point value that fails the integer checks. No registry either implementation writes can carry such a number, because epochs and sequence numbers are assigned upward from small counts, so the difference meets only a hand damaged registry, and it refuses earlier rather than later. A fraction on an offset whose whole part is zero is dropped by the Python instant parser and kept by this reader as the fraction of a second it names, a disagreement under one second that meets only a hand written offset, because no offset either implementation writes carries a fraction at all.

## Port repair note, the three reviews of the port

Recorded after the three reviews of the port, the red team re-audit and the spec fidelity axis and the standards axis, with the CodeRabbit findings read alongside them. The port amendment above stands, and this note corrects one of its sentences and records three deliberate changes of behaviour the reviews required. Everything the note does not name stands as the amendment left it.

The port amendment above says of integers wider than an unsigned 64 bit integer that no registry either implementation writes can carry such a number, because epochs and sequence numbers are assigned upward from small counts. That sentence is wrong on the write side. A claim on an item standing at the unsigned top added one and wrote a document carrying exactly such a number, a document the reader then refused, so one claim bricked the registry it claimed from. The read side refusal stands unchanged. The write side now fences. A claim on an item whose epoch already stands at the unsigned top is refused before any state changes, and the registry bytes stand unchanged, so no operation of this implementation can produce a document its own reader refuses.

Representability is now judged on the UTC instant that will actually be stored. The checks as first built read the wall clock year an offset carries, while the stored form is the UTC rendering, so a stored expiry late in the year 9999 at a negative offset renewed past the year line, and a current instant early in the year 1 at a positive offset passed validation with a UTC year of zero. The naive refusal stands, and an aware instant whose UTC rendering falls outside the years 1 to 9999 is refused at input validation, and a computed expiry outside those years in UTC is refused as an invalid time to live under DB-2, in both cases before any state changes.

The lock a command holds is now verified as the file standing at the lock path. Neither the port as first built nor the Python original checked that identity, so deleting the lock file while a claim worked let a second claim lock a fresh file and publish over the first, erasing a successful claim without a trace, against the one winner guarantee DB-1 states unconditionally. After the lock is taken its device and inode are checked against the path, with a bounded retry while the path settles, and the identity is checked again immediately before the publish. A command whose held lock is not the file at the path aborts with a failure and leaves the registry byte-identical. The invariant is that a claim which exits 0 is recorded, and a claim whose record could be silently erased exits 1 instead. This is a deliberate divergence from the Python original, recorded here with its reason. The port closes the hole rather than inheriting it silently.

The rest of the repair keeps behaviour and closes ground the reviews measured. The document validator tracks the item ids it has seen in a set rather than a list it scans, as the Python validator did, and the strict reader tracks the keys of an object the same way, so validation no longer grows with the square of the registry size. The instant reader accepts the basic week date spellings the Python fromisoformat accepts. The command line integer conversion accepts the decimal digits and the surrounding whitespace of the Python int conversion, the Unicode decimal digit families and the Unicode whitespace set, so the grammar the port amendment claims is the grammar the binary takes. The public instant constructors refuse what they cannot hold instead of panicking or wrapping, an offset at the edge of its type, a microsecond count past the width the type carries, and the formatter renders a naive instant as its wall clock fields with no offset suffix, the way the Python isoformat rendered it. The publish opens its temporary file exclusively, so a plant at the temporary name fails the publish instead of being followed. Two instants that name the same instant under different offsets now compare equal as well as ordered equal, as the Python datetimes did. The codepoint scanner narrows one sentence of its documentation to what its walk does. The fixture manifest redacts a working machine path from its embedded producer script, and the fixtures and their hashes are unchanged.

## Round 2 amendment, history and state cross validation

Amendment, recorded with the Round 2 cross validation slice. Obligation DB-7 above says the history lives in the registry document itself, so a state change and its history event publish in the same rename and the record cannot disagree with the state. The reader the port landed validated the items and the events each on their own fields and never joined the two halves, so a registry damaged by hand into a history that disagrees with its standing state read clean, and DB-7 claimed more than the reader checked. This amendment states the join as an obligation and the slice lands it. The format dibs-registry/1 does not change in any byte. The join is a reading strengthening only, and it refuses as corruption, in the message family DB-6 established, each disagreement it names. The Python implementation validated the two halves separately as well, so the join diverges from the Python behaviour deliberately, in the pattern of the lock identity repair the port recorded, because a reader that can see a disagreement and reads on has not validated the document whole.

The join checks, over the items and the history of one document, are these. Every event names an item that stands in the document. The events of one item, read in their recorded order, replay a passage of the life the writers write, and every event after the first recorded one follows from the events before it exactly as a writer would write it. An offer stands only as the first recorded event of its item, and no item is offered twice. No event stands after the item completes. A claim recorded as claimed stands over no standing lease, and a claim recorded as taken over stands over a standing lease and names the standing holder as the previous holder. A renewed or a released or a completed event stands over a standing lease and names the standing holder. A claim event, claimed or taken over, carries the epoch one past the standing epoch of its chain, and every other lease event carries the standing epoch itself. A takeover that opens the recorded events of its item carries an epoch of at least 2, because the lease it took over was itself a claim and a first claim carries epoch 1. The end of the replayed chain agrees with the standing item, in its status and in its epoch and, where the chain ends claimed, in its holder.

Three boundaries stand named, so the obligation claims only what the record can carry. An item that stands with no events at all is not refused by the join, and a history that opens in the middle of a life is not refused either, because the reader has always taken a standing item on its own fields, the standing pins at the epoch magnitudes and at the renewal edges rest on exactly that behaviour, and the writers themselves extend such a history one event at a time when a staged registry is claimed or renewed, so the join opens each chain at its first recorded event, governs every event that follows it, and checks the agreement of the chain end with the standing item, and invents no presence requirement the reader never had. Events carry no token hash and no expiry, by DB-4 and by the event shape itself, so the join compares holders and epochs and statuses only, and the truth of the expiry a takeover or a renewal turned on is not a recorded fact and is not joined. The instants the events carry are inputs the callers chose under DB-3, and no order over them is promised, so the join reads each chain in its recorded sequence and never in its instants. This is covered by damage tests that stage each named disagreement in a document the per field validation accepts whole and check the corruption error and that the registry bytes stand unchanged, by a control that reads every frozen fixture registry clean, and by life cycle tests that read the board and the history back after every operation the library writes.
